# Security 2026-10

This document is the second security audit of openconformity, made against commit `f2cfaf1` of 6 October 2026 on the develop branch. It reviews `docs/security.md` as a security model, for its structure, its method and its internal consistency, and then checks the model against the software, control by control, at that commit. It adds what the code audit found that the model does not yet hold, rated on the model's own scales so the rows can be carried over. Nothing in `docs/security.md` was changed by this audit. Where the model should change, the text is proposed here for the maintainer to paste. The target is openconformity. Cloudflare, GitHub and JGraph are boundaries the software depends on, and crossing them is described for what it means to the software, never planned as an attack on them.

## 1. Method

### 1.1 The document review

The model was read against the questions a threat model answers [1]. What is being built, what can go wrong, what is done about it, and whether the job was done well. Each chapter was then checked for the form good practice expects, assets ranked, boundaries drawn, actors named with their means, entry points enumerated, threats classified per boundary, scenarios rated for likelihood and impact before controls, controls traced to requirements, implementation and verification, and a residual risk stated and accepted on a ground [2][3]. The document was then read for consistency with itself, whether every identifier resolves, every status is one the conventions define, every rating follows the scales, and every verdict rests on a control that exists.

### 1.2 The code audit

Every module under `app/` was searched for the sinks and sources a browser application can be attacked through, markup construction, evaluation, dynamic import, network calls, reads of the address, the window name and the referrer, storage reads, message handlers, frame attributes, link construction and file construction. The modules on each trust boundary were then read in full, `dom.js`, `files.js`, `validator.js`, `drawing.js`, `drawing-cell.js`, `drawing-editor.js`, `store.js`, `theme.js`, `retention.js`, `fields.js`, `xlsx.js`, `markdown.js`, `zip.js`, and the parts of `editor.js`, `flows.js`, `shell.js`, `about.js`, `navigator.js`, `library.js`, `model.js` and `views.js` the model names. The page, the headers file, the policy files and the repository's own layout were read. Two claims were checked by running the modules in JavaScriptCore. The test suite was run. The host's live headers, the repository's settings and the accounts were not reachable from this audit and are marked as not verified.

### 1.3 Ratings

New findings carry the model's own feasibility, impact and risk, from its sections 1.2 to 1.4, so a finding that is adopted becomes a scenario row without translation. Findings on the document itself carry no rating.

## 2. The model as a document

### 2.1 What it does well

The model is better than most of what open-source projects publish, and better than many commercial ones. The points that stand out are listed so they are kept.

| Point | Why it matters |
|---|---|
| Read forward from threats to requirements | Every control names the requirement that holds it, where it is implemented and how it is verified. A control without a requirement is called a gap by the document's own rule, which is the right discipline. |
| STRIDE per boundary, with a row for every class | A class that does not apply is written as such, so a reader knows it was considered and not forgotten. |
| Risk rated before controls, verdict after | The two are kept apart, which makes the argument for acceptance readable. Most models blur them. |
| Assumptions, trusts and actors are explicit | AU, TR and TA rows say what the model rests on and who it defends against, so a reader can disagree with a premise rather than with a conclusion. |
| A reopen condition on every scenario | The evaluation says what would make each status false. That is what keeps a model alive, and it is rarely done. |
| A maintenance table | The triggers that oblige an update are listed by kind of change. |
| Retired rows keep their identifiers | The history of the model is readable from the model. |
| Pins in the test suite | Static checks that the policy, the sandbox and the absence of sinks hold at every run turn several controls from a review into a test. |

### 2.3 Method remarks

| Id | Remark |
|---|---|
| D-10 | The evaluation states what remains in words and rates it with a status, and never rates the residual on the scale of 1.4. Good practice accepts a risk at a stated level [2]. A Residual column with Low, Medium or High would make each Accepted row say what level was accepted, and would show at a glance that SC-14 accepts a High residual while SC-08 accepts a Low one. |
| D-11 | The risk table of 1.4 is a three-by-three matrix written as prose. It is correct and symmetric. A matrix drawing would read faster, but the prose is in keeping with the document's form. No change needed. |
| D-12 | The feasibility scale measures how easily an attacker reaches the scenario and the impact scale what it costs. Neither says how likely the attacker is to exist. For a free tool the threat actor who writes a hostile project file is real, so the omission costs nothing today. It is worth a sentence in 1.2 so a future reader does not add a likelihood axis without noticing it is missing on purpose. |
| D-13 | The controls are stated as requirements would be, and that is the right form. CT-16 and CT-17 say "Every module" as their implementation, which is true and unhelpful. The pin that enforces each is the implementation to name. |
| D-14 | Chapter 8 obliges an update per kind of change but names no owner for reading the reopen conditions at a release. The release review of 27 September holds that list. A sentence in chapter 8 pointing to it would tie the loop. |

## 4. Findings beyond the model

| Id | Finding | Actor | Feasibility | Impact | Risk |
|---|---|---|---|---|---|
| C-01 | No opener policy header. A page that opened the software with `window.open` keeps its handle on the tab, and a cross-origin opener may navigate the window it opened. While the user works, that page can send the tab to any address, such as a look-alike asking them to open their project file again. The software's own links leave without an opener, which guards the other direction only. | TA-05 | Medium | Medium | Medium |
| C-02 | The referrer leaves with a hyperlink. The anchor in `editor.js` `valueNode` carries `rel="noopener"` and not `noreferrer`, and `app/_headers` sets no referrer policy. Under the browser's default the click sends `https://app.openconformity.org/` to the address the file's author chose. What leaks is that the user uses the tool, not project content. The editor's frame already sends no referrer. | TA-01 | Medium | Low | Low |
| C-03 | A Markdown export autolinks. A cell holding `https://tracker.example/p?u=1`, `www.example.com` or `a@b.example` is written unchanged, confirmed by running `markdownCell`. GitHub, GitLab and most editors render each as a link. Nothing loads without a click and an image cannot form, since `[` is escaped. CT-36's statement that no field becomes a link does not hold on those renderers. | TA-01 | Medium | Low | Low |
| C-04 | The full policy is a meta element only. A meta policy takes effect where the parser meets it, cannot carry `frame-ancestors` or a reporting directive, and does not cover a response that is altered before the element. The host's header carries `frame-ancestors` alone. Carrying the same policy in the header as well, and keeping the meta for a folder served elsewhere, makes the policy cover the whole response. The header can also carry `require-trusted-types-for 'script'`, which makes the browser refuse every markup sink, the reopen condition of SC-01 enforced rather than reviewed, in the browsers that support it. | TA-08 | Low | High | Medium |
| C-05 | A prototype key passes the validator. `__proto__` as an attribute key opens and becomes an own property, harmless under AU-07 and proven by `test-validator.js:74`. The model's reopen condition says it should not pass. Refusing `__proto__`, `constructor` and `prototype` as attribute keys at the validator costs one line and removes the dependence on AU-07 for the file. No file the software writes can carry such a key, so no version 1 file is refused by the change. | TA-01 | High | Low | Medium |
| C-06 | The path to main is unverified and unsigned. Every commit read is unsigned. No workflow runs the suite on push, so CT-30 rests on the maintainer's habit. Branch protection could not be read. The host deploys main within minutes, so TH-43 and TH-48 are one credential away. They add nothing to the software. | TA-08 | Low | High | Medium |
| C-07 | The headers file could say more. ## 7. Verdict

The model is well structured and follows a sound method. It asks the right questions in the right order, keeps likelihood apart from the effect of controls, and ties every control to a requirement, a place in the code and a check. Its weaknesses are of bookkeeping, a status it does not define, an actor it does not name, a boundary with half its rows, a reopen condition already true, and a release check not recorded for the current release.

The software holds what the model claims at commit `f2cfaf1`, with one gap. The Markdown export lets a bare address become a link in the renderers most people use, which is the lowest impact of the three exit routes CT-36 names. Beyond the model, the two headers the host does not send, an opener policy and a referrer policy, are the findings worth a commit this week. The path to main is the one risk the model accepts that this audit would not leave as it stands, and the cheapest control is a required check the repository runs itself.

Nothing found runs code, reads the project or leaves the device. No finding is High.
